## 2. Что именно проверяет `verify-m3.sh`

1. **Boot + привязки.** Ядро поднимается, в логе `notify extension installed` и `notify tasks
   scheduled`; в `pi_tasks` ровно две живые задачи (`hmwrk.reminder`, `hmwrk.digest`); в `users` две
   строки — по одной на статический ключ (I3 заводит их на старте, иначе `bind-telegram.ts` не к чему
   привязывать чат). `scripts/bind-telegram.ts parent 111` и `… child 222` кладут две строки в
   `tg_bindings`.
2. **`set_setting` из чата.** Родитель просит поставить напоминание/дайджест на ближайшее время:
   инструмент отвечает «Расписание напоминаний пересобрано: ближайшее сработает уже в новое время»
   (то есть durable-задачи были пересозданы, а не оставлены спать до следующего дня). После двух
   пересборок живых задач по-прежнему ровно две.
3. **Данные для рассылок.** Родитель добавляет «Математика <5.1>» (дедлайн — завтра 20:00) и
   «Литература & чтение» (завтра 21:30); ребёнок отчитывается по математике фото → `checkins`,
   durable-задача `hmwrk.verify` даёт черновик вердикта (faux); родитель добавляет просроченный
   «Русский язык»; родитель присылает скриншот дневника → `parse_screenshot` отвечает
   структурированным черновиком («Разобрал 1 фото в черновик заданий», «География», «§ 12»), в
   `photos` строка с `kind=screenshot` (фото ребёнка — `kind=checkin`).
4. **Напоминание ребёнку.** В `reminder_time` в чат ребёнка приходит сообщение с заданием на
   **завтрашний** вечер (это и есть исправленное окно сбора, §4): «Литература &amp; чтение»,
   «стр. 40», подпись «Не забудь отчитаться». Уже сданная математика и просроченный русский в
   напоминание не попадают; данные экранированы (`&amp;`, а не `&`), `parse_mode: HTML`.
5. **Дайджест родителю.** В `digest_time` в чат родителя приходит «Итоги дня» с тремя секциями:
   «Сдано сегодня» (с комментарием ребёнка), «Просрочено» (русский), «Ждут утверждения» (резюме
   черновика). Тема с `<` экранирована (`Математика &lt;5.1&gt;`), `parse_mode: HTML`, в логе
   `notify: message delivered`.
6. **Пауза.** Родитель ставит `paused_until` на сегодня и сдвигает `digest_time` на новое окно:
   задача срабатывает (в логе `notify: broadcasts are paused, nothing is sent`), но в чат родителя
   **не приходит ни одного сообщения** — пауза глушит ближайший fire, а не следующий день.

## 3. Фактическая модель планирования (что вышло)

- **Две вечные sleeping-задачи** (`hmwrk.reminder`, `hmwrk.digest`), владелец — household-root
  беседа. Никакого cron: задача спит через `sleepUntil`, просыпается, отправляет, снова спит.
- **Рестарт.** Задачи — durable-записи: после падения/`SIGTERM` они остаются в `pi_tasks` и
  восстанавливаются `resume()`. Boot вызывает `createNotifyScheduler(core).ensureScheduled()`:
  он ищет живую (не терминальную) задачу каждого вида и создаёт недостающую. Проверено юнит-тестом
  (`boot.test.ts`): второй boot поверх того же файла возвращает **те же id** и не добавляет задач
  (`SELECT kind, count(*) … = 1/1`).
- **Смена времени из чата.** `set_setting` (`reminder_time`, `digest_time`) вызывает
  `NotifyScheduler.reschedule()`: обе живые задачи завершаются (`aborted`), `ensureScheduled()`
  создаёт новые, и их первая фаза `schedule` читает уже новое время. Итог: **новое время применяется
  к ближайшему окну**, а не «со следующего цикла». Если задача не успела стать терминальной за 2 с
  (`RESCHEDULE_WAIT_MS`), изменения просто применятся со следующего цикла — это логируется
  (`notify: the previous task did not end in time…`) и не ломает настройку. Сломанный хук
  (например, упавший scheduler) тоже не отменяет сохранение значения — тест на это есть.
- **`paused_until`** пересборку не требует: значение читается в фазе `fire`, поэтому гасит именно
  ближайший fire (проверено и юнит-тестом N1, и e2e).
- **Нет токена — нет задач.** Без `TELEGRAM_BOT_TOKEN` notify-расширение не устанавливается,
  планировщик не создаётся, в логе одна строка уровня `info`
  (`TELEGRAM_BOT_TOKEN is unset: reminder and digest are not scheduled`). Это позволяет M1/M2
  прогонам оставаться без Telegram.

## 4. Окно сбора напоминания (решение журнала §7 по находке N1)

Было: `[now, now + 24h)`. Стало (`src/durable/tasks/notify.ts`):

```ts
/** now <= due_at < startOfLocalDay(now + 2 суток) — до конца следующих локальных суток. */
export function reminderHorizon(now: Date): Date {
  return startOfLocalDay(addLocalDays(now, 2));
}
```

То есть напоминание в 19:00 видит всё, что нужно сдать до полуночи **завтрашнего** дня, включая
дефолтный дедлайн «завтра 20:00» — ровно случай, который SPEC §5.6 и называет («завтра сдать»).
Задание на послезавтра 00:01 в окно не попадает. Оба края закреплены тестами
(`notify.test.ts`: «reaches the end of tomorrow…», «stops at local midnight after tomorrow…»), а
e2e проверяет фактический текст сообщения.

## 5. Фолбэк `requestId` (шов P2)

`deriveRequestId` теперь хэширует `user + model + messages + состояние беседы`. Состояние — id
последней записи беседы (`tx.latestEntryId` в write-free коммите), то есть монотонный счётчик
истории:

- ретрай того же запроса **в том же состоянии** → тот же ключ → та же submission, второго прогона нет
  (идемпотентность M2 сохраняется; явный `X-Request-Id` по-прежнему главнее);
- те же слова **после новых событий** (предыдущий ответ, отчёт, вердикт) → другой ключ → новый ход.
  Именно это чинило баг M2, где второй настоящий вопрос возвращал закэшированный ответ.

Если состояние прочитать нельзя (тестовый fake-core без harness, ошибка чтения), функция ведёт себя
как до I3 — есть юнит-тест на оба случая (`routes.test.ts`).

## 6. Что требует живых ключей/токена Telegram

Faux-прогон доказывает склейку, расписание и доставку, но **не** живой Bot API и не качество моделей:

| Что | Чем проверяется | Что нужно |
|---|---|---|
| Токен бота, права, chat_id | `getMe` + тестовое сообщение | живой `TELEGRAM_BOT_TOKEN`, «Start» в чате у бота |
| Реальная доставка по расписанию | вечером в 19:00/21:00 | токен + привязанные чаты (`bind-telegram.ts`) |
| Чтение почерка (Groq vision) | отчёт ребёнка фото | `GROQ_API_KEY`, id модели в `models.json` |
| Вердикт JSON (Mistral) | «что по проверкам?» | `MISTRAL_API_KEY` |
| OpenWebUI-заголовки (`X-OpenWebUI-User-Id`) | чек-лист G1 | вход в OpenWebUI под нужной ролью + строка в `users` |

Ручной смоук (после `npm start` с ключами и токеном):

1. `node --import tsx scripts/bind-telegram.ts parent <chat_id>` и `… child <chat_id>`;
2. в чате родителя: «напоминай в 18:30» → ответ «Расписание напоминаний пересобрано…»;
3. в чате ребёнка: фото тетради + «сделал математику» → «Отчёт принят… на проверке»;
4. вечером: ребёнку приходит напоминание, родителю — дайджест; «поставь паузу на сегодня» убирает
   вечернюю рассылку.

Ошибки Bot API разбираются по `description` (`400 can't parse entities` — сломан HTML в шаблоне,
`403 bot was blocked` — нажать Start, `429 … retry_after` — лимит, повтор не делается: следующее окно
— завтра). Подробности — `docs/telegram-setup.md`.
