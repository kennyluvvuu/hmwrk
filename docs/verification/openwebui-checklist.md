# Чек-лист: OpenWebUI ↔ hmwrk (ручной прогон, checkpoint риска №3)

Это ручной шаг на домашнем сервере — его выполняет юзер, а не код. Задача: подтвердить,
что OpenWebUI видит ядро, что обе роли получают ответ, и снять факт по заголовкам
(передаёт ли OpenWebUI идентичность пользователя на OpenAI-коннекцию). От результата зависит,
какой механизм ролей закрепляем в SPEC §4: заголовки (а) или два статических ключа (б).

Подготовка: пройден `docs/setup-openwebui.md`, в `deploy/.env` стоит `LOG_LEVEL=debug`, в
одном терминале открыто `cd deploy && docker compose logs -f hmwrk`, `git status` не важен —
это не кодовая задача. Отмечай пункты по порядку; если пункт не прошёл — сначала таблица
«Симптом → что проверить» в гайде, потом пиши в тред с выводом логов.

## A. Стенд

- [ ] 1. `docker compose ps`: `hmwrk` — `healthy`, `open-webui` — `Up`. Никто не в `restarting`.
- [ ] 2. В логах ядра есть `"msg":"role resolver configured"` и `"mode":"static-keys"` — зафиксировать этот факт (он объясняет, почему роли пока по ключу).
- [ ] 3. `docker compose exec hmwrk node -e 'fetch("http://127.0.0.1:8787/healthz").then(r=>r.text()).then(console.log)'` → `{"status":"ok"}`.
- [ ] 4. `http://<хост>:3000` открывается, вход выполнен аккаунтом родителя, у него есть `Admin Panel` (роль `admin`).

## B. Родитель и коннекция

- [ ] 5. `Admin Panel → Settings → Connections`: коннекция с `URL = http://hmwrk:8787/v1` и ключом `HMWRK_PARENT_KEY` сохранена, ошибок у неё нет.
- [ ] 6. В селекторе моделей есть модель ядра (`hmwrk`, а после шага 7 гайда — `parent.hmwrk`).
- [ ] 7. Родитель отправил `проверка связи` — пришёл **тот же текст** (echo M1).
- [ ] 8. В логах ядра появилась строка `"msg":"chat completion"` с `"userId":"key:parent"` и `"role":"parent"`; `conversationId` выписать.

## C. Заголовки с первого запроса (главный пункт checkpoint)

- [ ] 9. `ENABLE_FORWARD_USER_INFO_HEADERS=True` выставлен для `open-webui` (`docker-compose.override.yml`, см. гайд шаг 6), стек перезапущен (`docker compose up -d`).
- [ ] 10. Запущен «шпион» из гайда (шаг 6), к нему добавлена коннекция `http://headerspy:8799/v1` с `Prefix ID = spy`.
- [ ] 11. Родитель отправил одно сообщение в `spy.hmwrk`, ребёнок — одно сообщение в `spy.hmwrk`; в терминале шпиона два JSON-объекта с заголовками. **Вывод сохранён целиком** (его и присылаем в тред).
- [ ] 12. Прочитано и записано словами: есть ли `x-openwebui-user-id` / `-user-name` / `-user-email` / `-user-role` / `x-openwebui-chat-id`; какие значения пришли у родителя и у ребёнка (id пользователя должен отличаться).

## D. Ребёнок

- [ ] 13. Аккаунт ребёнка создан с ролью `user` (не `admin`, не `pending`), вход под ним работает, `Admin Panel` у него нет.
- [ ] 14. Ребёнок видит только разрешённую ему модель (`child.hmwrk` при механизме (б)) и **не видит** модель родителя; если модели нет — это ожидаемый минус, записать как есть.
- [ ] 15. Ребёнок отправил `проверка связи` → пришёл тот же текст; в логах ядра `"role":"child"` (при механизме (б) — `"userId":"key:child"`).

## E. Перезапуск и сохранность

- [ ] 16. `docker compose restart hmwrk`, дождаться `healthy`.
- [ ] 17. Тот же аккаунт отправил ещё одно сообщение: ответ echo приходит, а `conversationId` в логе **совпадает** с выписанным в п. 8 (беседа не началась заново).
- [ ] 18. `docker compose down && docker compose up -d`: аккаунты, подключения и история чатов в OpenWebUI на месте (volume `open-webui-data`), ядро снова `healthy` (volume `hmwrk-data`).

## Что в M1 не проверяем (просто держим в голове)

Ядро в M1 — echo-скелет: доменные сценарии спеки ещё не реализованы и провалидировать их
здесь нельзя. Их проверка — вехи M2/M3, каждый своим чек-листом:

- загрузка скриншота дневника и ручное добавление задания (родитель);
- список активных заданий для обеих ролей;
- отчёт ребёнка по заданию (кнопка/фраза + фото тетради);
- verify-конвейер, вердикты (черновик → утверждение родителем) и «unclear» вместо угадывания;
- напоминания и дайджест, настройки из чата (времена, `paused_until`);
- разграничение инструментов по роли (в M1 инструментов нет);
- Telegram/Slack: внешних каналов нет по спеке (бот — только исходящая рассылка, с M3), поэтому в этом чек-листе их нет.

## Что прислать в тред

1. Вывод шпиона с заголовками **первого запроса от каждого аккаунта** (п. 11) — целиком, включая `GET /v1/models` и `POST /v1/chat/completions`.
2. Скриншот `Admin Panel → Settings → Connections` (видно URL, префиксы; ключи не показывать/замазать).
3. Строки логов ядра: `role resolver configured`, по одной `chat completion` от родителя и от ребёнка из пп. 8/15, и обе `conversationId` из п. 17.
4. Скриншот селектора моделей под аккаунтом ребёнка (п. 14) — что именно ему видно.
5. Список пунктов, которые не прошли, с текстом ошибки из UI или логов.

По этому набору фиксируем механизм ролей: заголовки (а) — отдельной задачей после D2
(таблица `users` + передача справочника в `bootstrap`), либо статические ключи (б) как
основной путь с правкой SPEC §4.
