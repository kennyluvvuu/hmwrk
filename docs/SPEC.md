# hmwrk — спецификация (v0.1)

Статус: черновик, зафиксированный по итогам интервью 24.11. Срок жизни: до первого тупика в реализации, дальше правится.
Словарь домена — [GLOSSARY.md](../GLOSSARY.md), архитектурные решения — [docs/adr/](adr/).

## 1. Цель

Родитель перестаёт быть единственным трекером домашнихних заданий: задания попадают в систему из скриншота электронного журнала, ребёнок отчитывается с фото тетради, AI проверяет правильность и полноту, родитель только утверждает вердикты и читает вечерний дайджест. Главный сценарий: «ребёнок не отчитался — родитель узнал об этом из дайджеста», а не «не отчитался — узнал от классного руководителя через неделю».

## 2. Решения (кратко)

| Развилка | Решение | Где зафиксировано |
|---|---|---|
| Интерфейс | OpenWebUI как основа UI; своего веб-UI в MVP нет | ADR 0001 |
| Агентное ядро | Node/TS поверх `@earendil-works/pi-durable`, модели через `@earendil-works/pi-ai` | ADR 0002 |
| Владелец агентного цикла | Ядро; наружу OpenAI-совместимый `/v1/chat/completions`, OpenWebUI — клиент | ADR 0003 |
| Аккаунты/роли | Два аккаунта OpenWebUI; ядро маппит user → роль | ADR 0004 |
| Модели | Свои ключи: Groq (vision) + Mistral (текстовая проверка DeepSeek) | разд. 7 |
| Деплой | Docker Compose на домашнем сервере, Telegram long polling (публичный IP не нужен) | разд. 9 |
| Telegram-бот | Только рассылка (напоминание ребёнку + дайджест родителю) | разд. 6 |
| Проверка | Правильность ответов + полнота выполнения; черновой вердикт утверждает родитель | ADR 0002, разд. 5.4 |
| MVP | Полный цикл ДЗ + ручное добавление + настройки из чата; скриншот-интэйк — отладочное качество | разд. 10 |

## 3. Архитектура

```
 ┌────────────┐  OpenAI-совместимый    ┌──────────────────────────────┐
 │  OpenWebUI │ ──/v1/chat/completions▶│  ядро hmwrk (Node/TS)        │
 │ (родители и│       user-контекст    │  · агент на pi-durable        │
 │   ребёнок) │                       │  · durable-задачи: проверка,  │
 └────────────┘                       │    напоминание, дайджест       │
                                      └───┬──────────┬───────────┬───┘
                                          │          │           │
                                   SQLite (файл)   LLM API     Telegram Bot API
                                   задания, отчёты, (pi-ai)    sendMessage only
                                   вердикты, настройки ┌─────────────┐
                                          │           │              │
                                       фото на диске  ▼              ▼
                                                   Groq vision   напоминания,
                                                   Mistral текст  дайджест
```

- **Ядро** — единственный держатель доменного состояния и агентной логики. OpenWebUI легко заменить на другой чат-клиент: снаружи виден только OpenAI-совместимый эндпоинт.
- **Durable-задачи** (проверки, напоминания, дайджест) живут в планировщике pi-durable (SQLite): сервер перезагрузился mid-task — задача продолжилась с последнего checkpoint.
- **Telegram** — только исходящие (`sendMessage`), long polling не используется вовсе: доставляем по таймерам durable-задач. Входящих вебхуков нет, публичная экспозиция ядра не нужна.

## 4. Акторы и доступ

| | Родитель | Ребёнок |
|---|---|---|
| Идентификация | аккаунт OpenWebUI | аккаунт OpenWebUI |
| Загрузка скриншота, ручное добавление задания | ✔ | — |
| Отчёт по выполнению (кнопка/фраза + фото тетради) | — | ✔ |
| Просмотр вердиктов | все, включая черновики | только утверждённые |
| Утверждение/отклонение вердикта | ✔ | — |
| Настройки (времена, пауза) | ✔ | — |
| Список активных заданий | ✔ | ✔ |

Механизм ролей: ядро получает user-контекст из заголовков OpenWebUI, таблица `users(openwebui_user_id, role)` отображает его в роль; инструменты агента проверяют роль. Fallback, если заголовки не настроатся: два статических API-ключа ядра (parent/child) и две «модели» в OpenWebUI с разграничением группами. Выбранный механизм фиксируем при первом подключении OpenWebUI (checkpoint интеграции).

## 5. Доменная модель и флоу

### 5.1 Состояния

```
Assignment:  active ──отчёт──▶ in_review ──утверждён──▶ done
                │                 │
                └─ дедлайн прошёл ┘──▶ overdue (производная: без отчёта после дедлайна)
```

- `in_review` — отчёт есть, идёт или ждёт проверки/утверждения. Отчёт можно дополнить фото — тогда вердикт пересчитывается (до утверждения).
- `overdue` не хранится, вычисляется: `active && due_at < now`.

### 5.2 Таблицы (SQLite, файл один)

| Таблица | Поля (сокращённо) |
|---|---|
| `assignments` | id, subject, due_at, source: screenshot\|manual\|journal, status, created_at |
| `assignment_items` | id, assignment_id, label («№ 12»), note |
| `checkins` | id, assignment_id, child_user_id, created_at |
| `checkin_photos` | checkin_id, photo_id |
| `photos` | id, path, mime, created_at |
| `verifications` | id, checkin_id, status: draft\|approved\|dismissed, summary, model, created_at, decided_at |
| `verification_findings` | verification_id, item_id, verdict: ok\|wrong\|missing\|unclear, comment |
| `users` | openwebui_user_id, role: parent\|child, name |
| `tg_bindings` | user_id, chat_id |
| `settings` | key, value (json): reminder_time, digest_time, default_due, paused_until |

Фото — файлы в `data/photos/`, в базе только пути. Скриншоты-источники — там же, отдельная подпапка: groundwork для будущего парсера журнала.

### 5.3 Интэйк (debug-grade)

Скриншот attaches в чат → инструмент `parse_screenshot` → Groq vision возвращает структуру `[Assignment{subject, due, items}]` → агент печатает человеку-читаемый список («Математика, к 25.11: №12, №13, №14») → родитель правит/подтверждает → **активные задания**. Ручное добавление: фразой «добавь задание: математика, №12–14, к 25.11» без скриншота — тот же результат, инструменты те же.
Промежуточная таблица «черновиков парсинга» не заводится: подтверждение — это просто создание заданий, отмена — ничто не создаётся.

Явный скоуп-флаг: **флоу скриншота — отладочный канал**. Полировка UX парсинга (массовое редактирование, повторные скрины, слияние с существующими) не делаем: на подходе парсер электронного журнала, который займёт место основного источника (`source: journal`). Интерфейс инструментов интэйка пишем так, чтобы источник заменялся без переделки домена.

### 5.4 Отчёт и проверка

1. Ребёнок в чате: «сделал математику» + фото тетради → `submit_check_in(assignment, photos)` → Assignment = in_review → стартует durable-задача `verify`.
2. **Прочтение**: Groq vision транскрибирует фото в текст решений (по пунктам).
3. **Проверка**: текстовая модель (DeepSeek через Mistral) решает задания сама и сверяет с прочитанным: по каждому пункту вердикт `ok | wrong | missing | unclear` + короткий комментарий; `unclear` — честный сигнал «не разобрал почерк/номер», а не угад.
4. Итог — `verification(status=draft)` + резюме для родителя. Ребёнку в чате: «принято, проверяю».
5. Родитель в чате видит черновой вердикт (инструмент `get_verdicts` / агент сам поднимает при вопросе «что там по проверкам») → `approve_verification` / `dismiss` → Assignment = done. После утверждения ребёнок видит результат.

Модель может ошибиться и в прочтении, и в решении — поэтому вердикт AI — всегда **черновик**, финальная инстанция — родитель (выбрано ещё в первом раунде, без tutor-разбора ошибок для ребёнка в MVP).

### 5.5 Инструменты агента (единый список)

`list_assignments`, `parse_screenshot`, `manual_add_assignment`, `submit_check_in`, `get_verdicts`, `approve_verification`, `dismiss_verification`, `get_settings`, `set_setting`. Разрешения — из разд. 4; агент получает роль в системном промпте и не предлагает недоступные действия. Валидация аргументов — zod-схемы, кривые аргументы → человекочитаемая ошибка агенту.

### 5.6 Уведомления (Telegram, только рассылка)

- **Напоминание ребёнку** (durable sleeping task): в `reminder_time` (дефолт 19:00) пробегаем задания с `due_at` в ближайшие сутки без отчёта → одно сообщение со списком «завтра сдать: математика №12, английский упр. 3 — не забудь отчитаться».
- **Дайджест родителю** (durable задача по расписанию, дефолт 21:00): что сдано сегодня, что просрочено, какие вердикты ждут утверждения, что пришло от парсера скриншотов на подтверждение.
- Точечные алерты «не отчитался» в момент дедлайна — **осознанно не делаем** (заменены дайджестом; вернуть — одна durable-задача, если дайджеста не хватит).
- `paused_until` (каникулы/отпуск) глушит обе рассылки.

### 5.7 Настройки из чата

`set_setting("reminder_time", "19:00")`, `set_setting("digest_time", ...)`, `set_setting("default_due", "20:00 след. дня")`, `set_setting("paused_until", "2026-01-09")`. Дефолты: дедлайн «завтра 20:00» (школьный календарь в MVP не заведён; парсер журнала потом принесёт точные даты, ручные — правятся при создании).

## 6. Диалоги и память

- Один агент-«модель» на роль виден в OpenWebUI (id: `hmwrk`). Сессии: у каждого пользователя своя durable-беседа (pi-durable conversation), история переживает рестарт ядра; OpenWebUI дополнительно хранит чат-историю у себя (двойного хранения не боимся: у ядра — рабочая память агента, у OpenWebUI — UI-история).
- Системный промпт агента: роль, текущие активные задания (краткая сводка), доступные инструменты, формат дат.
- Стриминг ответа — SSE в формате OpenAI Chat Completions (без него OpenWebUI будет показывать «думает…» до конца генерации).

## 7. Модели (pi-ai, конфиг per-task)

| Слот | Провайдер | Пример | Задача |
|---|---|---|---|
| `read` | Groq | vision-модель | прочтение скриншотов и фото тетрадей |
| `verify` | Mistral | DeepSeek | решение заданий и сверка с прочитанным |
| `chat` | Mistral | DeepSeek | та же или другая текстовая: диалог агента |

Конкретные model id — в конфиге, не в коде. Ключи: `GROQ_API_KEY`, `MISTRAL_API_KEY`. pi-ai даёт единый клиент над OpenAI-совместимыми API; смена провайдера/модели = правка конфига (пользователь явно просил не зашивать).

## 8. Кодовая структура

```
src/
  config/        env, models.json, дефолты настроек
  domain/        типы, zod-схемы, репозитории (SQLite через pi-durable storage)
  durable/       harness, задачи: verify, reminder, digest
  agent/         системный промпт, инструменты (5.5), разрешения по роли
  server/        Hono: /v1/chat/completions, /v1/models, /healthz
  telegram/      клиент Bot API, bindings, шаблоны сообщений
data/            sqlite-файл, photos/
deploy/          docker-compose.yml, .env.example
```

## 9. Деплой

Docker Compose, домашний сервер: `open-webui` (порт 3000 наружу, том данных) + `hmwrk` (собирается из Dockerfile, порт наружу не публикуем — только внутри сети compose; OpenWebUI ходит в него по `http://hmwrk:8787/v1`). Telegram — исходящие HTTPS-запросы, публичный IP/домен не нужен. Volumes: данные OpenWebUI, `hmwrk-data` (SQLite + фото). Рестарт сервера безопасен: durable-задачи доеживают и продолжаются.

## 10. Границы MVP и non-goals

В MVP: полный цикл (инсайк скриншота/ручной → отчёт → проверка → утверждение), напоминания + дайджест, настройки из чата.

| Non-goal | Судьба |
|---|---|
| Парсер электронного журнала | главный кандидат следующего контура; интерфейс интэйка под него рассчитан (`source: journal`), полировку скриншотного флоу не делаем |
| История/статистика по неделям | второй кандидат; все события уже в SQLite — будет агрегат без миграций |
| Отчёт ребёнка из Telegram, inline-кнопки | отклонено (второй канал отчётов); бот — только рассылка |
| Точечные алерты родителю в момент дедлайна | заменены дайджестом |
| Tutor-разбор ошибок для ребёнка | вне MVP (родитель — посредник) |
| Школьный календарь/расписание | нет; дедлайны задаются явно |
| Мульти-дети | домен параметризован `users`, флоу и UI тестированы на одном |

## 11. Риски и открытые точки

1. **Экспериментальный API pi-durable** — пин точной версии, тонкая обёртка над harness в `src/durable/` (ADR 0002).
2. **Достоверность прочтения рукописного** — `unclear` вместо угадывания; вердикты требуют утверждения; если Groq-модель стабильно путает почерк — сорс-модель меняется конфигом.
3. **Механизм передачи user-контекста OpenWebUI → ядро** — проверить заголовки user-info на поверхности OpenAI-соединения; fallback — ключи-per-role (разд. 4). Единственная интеграционная точка со сторонним продуктом, где спека может встрять о реальность.
4. **Ребёнок и «стоп-кран»** — при плохом опыте (спам напоминаниями,/formализация общения) мотивация падает; времена и `paused_until` — первые ручки подкрутки.
5. **День дедлайна = «завтра»** — дефолт с ручной правкой; скриншот без даты → агент уточняет.

## 12. Вехи
